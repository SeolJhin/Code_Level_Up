Q1. forEach, map, filter 차이점
A1.
    공통점 : 배열순회 메서드
    차이점 : 
                forEach : 반환값이 없는 출력 저장용 
                map : 각 배열 요소를 변환해서 새 배열 생성
                filter : 조건을 만족하는 요소만 반환

                const nums = [1, 2, 3, 4, 5];

                // forEach: 반환값 없음, 부수 효과(출력, 저장 등)용
                nums.forEach(n => console.log(n));
                // 1 2 3 4 5 출력, 반환값은 undefined

                // map: 각 요소를 변환해서 새 배열 생성
                const doubled = nums.map(n => n * 2);
                // [2, 4, 6, 8, 10]

                // filter: 조건을 만족하는 요소만 남김
                const evens = nums.filter(n => n % 2 === 0);
                // [2, 4]

Q8. MSA(Microservice Architecture) 와 Monolithic 장단점
A8. 
    Monolithic : 
        pros - 
            개발/배포 단순, 초기 개발속도 빠름, 인프라 설계부담 적음, 디버깅테스트 쉬움, 트랜잭션 간단함, 성능이 좋음(네트워크 호출 없이 메서드 호출로)
        cons -

        MSA : 
    pros - 
        독립 배포 가능, 부분 확장 가능, 장애 격리 가능, 기술 스택 자유도 증가, 팀 단위 자율성 증가, 개별 서비스의 이해도가 증가

Q9. 본인이 사용한 각 DB의 장단점
A9. oracle(교육때 무료버전) vs mysql vs postgresql
    1. Oracle
        상용, 유료, 엔터프라이즈 안정성, 대용량, 금융-공공-대기업, PL/sql
    2. MySql
        오픈소스, GPL, 상용 이중, 단순-빠름, 웹 서비스-스타트업, 저장 프로시저
    3. PorstgreSQL
        오픈소스 ORDBMS, PostgreSQL License (BSD 계열, 완전 자유), 표준 준수, 확장성-전용고급 기능, 데이터 중심 서비스분석-GIS, PL/pgSQL (+ Python 등 다양)
    세 DBMS는 모두 관계형 데이터베이스이지만 출발점과 철학이 다릅니다. Oracle은 대기업과 금융권의 요구에서 성장한 상용 제품이고, MySQL은 웹 서비스의 빠른 개발과 단순함을 중심으로 퍼진 오픈소스이며, PostgreSQL은 학계에서 출발해 표준 준수와 확장성을 중시하며 발전한 오픈소스입니다. 그래서 같은 SQL을 쓰더라도 어떤 환경에서 어떤 문제를 풀기 좋은지가 서로 다릅니다.

    Oracle은 엔터프라이즈 환경에서 가장 오래 검증된 상용 RDBMS입니다. RAC(클러스터), Data Guard(이중화), 파티셔닝, 고급 옵티마이저 등 대규모 트랜잭션과 고가용성에 필요한 기능이 가장 풍부하고, PL/SQL로 DB 안에 복잡한 비즈니스 로직을 구현하는 사례도 많습니다. 벤더 기술 지원과 숙련된 인력 풀이 확실해 금융, 공공, 대기업에서 널리 쓰입니다. 반면 코어 수 기반의 라이선스 비용이 매우 크고, 운영과 튜닝 난이도가 높아 DBA 의존도가 큽니다. PL/SQL 로직이 쌓일수록 다른 DB로 옮기기 어려운 벤더 종속 문제도 있으며, 클라우드와 컨테이너 환경에서의 유연성도 상대적으로 떨어집니다.

    MySQL은 설치와 사용이 쉽고 학습 곡선이 낮아, 읽기 위주의 단순한 웹 서비스에서 가볍고 빠르게 동작합니다. 자료와 커뮤니티가 방대하고 AWS RDS, Aurora 같은 호스팅 지원도 풍부하며, 복제(Replication) 구성이 간단해 읽기 확장에 유리합니다. 다만 고급 기능은 상대적으로 부족한 편이었습니다. 최근 버전에서 윈도우 함수와 CTE가 추가되며 많이 개선되었지만, 복잡한 쿼리나 대용량 분석에서는 옵티마이저가 약한 편이고 SQL 표준 준수도도 낮습니다. 스토리지 엔진에 따라 동작이 달라지지만 현재는 InnoDB가 사실상 표준입니다. 또한 Oracle社가 소유하고 있어 라이선스와 향후 방향성에 대한 우려가 있고, 이 때문에 MariaDB 같은 포크가 존재합니다.

    PostgreSQL은 SQL 표준 준수도가 높고 기능이 풍부한 오픈소스 DB입니다. CTE, 윈도우 함수, 부분 인덱스, 배열 타입을 지원하고, 인덱싱이 가능한 JSONB 덕분에 관계형과 문서형을 함께 쓸 수 있습니다. PostGIS(지리 정보), pgvector(벡터 검색), TimescaleDB 같은 확장(Extension)으로 기능을 넓힐 수 있고, MVCC 기반의 동시성 처리가 우수해 복잡한 쿼리에 강합니다. 라이선스가 BSD 계열이라 완전히 무료이며 벤더 종속도 없습니다. 단점으로는 MVCC 때문에 생기는 dead tuple을 정리하는 VACUUM과 autovacuum 튜닝 같은 운영 지식이 필요하고, 단순 읽기 워크로드에서는 MySQL보다 설정과 튜닝이 더 필요할 수 있습니다. 복제와 HA 구성도 기본 기능만으로는 번거로워 Patroni 같은 별도 도구를 쓰는 경우가 많고, 국내 공공이나 레거시 영역에서는 Oracle에 비해 사례와 인력이 적은 편입니다.

    

Q10. 설계 할때 어떤걸 가장 고려해서 설계 하는지
A10. 
    교육 당시는 프론트(리액트)단부터 백엔드(sts)단 까지 하드코딩으로 기본적인 로직과 버퍼관리, 네트워크에 대한 기초이론, 조건-반복문 을 배웠고 프로젝트에 진입하면서 직접 기획과 UI(wire_frame_work) 설계를 통해 요구사항 명세서를 작성했습니다. 거기서 발생할 데이터들을 전부 entity로 옮기며 다시 역으로 백엔드단부터 프론트단까지 하드코딩으로 작업했습니다. 따라서 생각을 하고 설계를 했다기보단 먼저 기획부터하고 멘토님과 강사님께 검토받으며 진행했다고 말씀드리는게 맞습니다. 배운점은 데이터무결성, 정규화레벨과 이슈, 쿼리 패턴, 확장성, 변경 용이성, 동시성 제어, 네이밍에 대한 이론을 후에 학습했습니다.

    이제 앞으로 설계를 한다면, 가장 먼저 "이 데이터를 어떤 쿼리로 가장 많이 조회하고 변경하는가" 를 정리하는 것부터 시작하겠습니다. 교육 당시에는 화면(UI)에서 출발해 필요한 데이터를 entity로 옮기는 방식이었다면, 이제는 쿼리 패턴과 데이터 간 관계를 먼저 정의하고 그에 맞춰 테이블과 인덱스를 설계하겠습니다.

    그다음 데이터 무결성을 애플리케이션 코드에만 맡기지 않고 PK/FK, UNIQUE, NOT NULL, CHECK 같은 제약조건으로 DB 레벨에서도 한 번 더 보장하겠습니다. 테이블은 기본적으로 3정규형까지 정규화해 삽입, 갱신, 삭제 이상을 막고, 조회 성능이 실제로 문제가 되는 구간에서만 근거를 가지고 반정규화하겠습니다.

    또한 선착순 이벤트처럼 동시에 요청이 몰리는 기능은 설계 단계에서부터 동시성 제어(락 방식, 격리 수준, Redis 같은 원자 연산)를 고려하고, 요구사항이 바뀔 것에 대비해 Flyway 같은 마이그레이션 도구로 스키마 변경 이력을 관리하겠습니다. 마지막으로 네이밍과 타입(금액은 DECIMAL, 시간은 UTC 등) 규칙을 팀 단위로 먼저 합의해 일관성을 유지하겠습니다.

    그리고 혼자 판단하기보다, 교육 때처럼 멘토나 팀원에게 설계를 검토받는 과정을 계속 유지하겠습니다. 설계는 한 번에 완성되는 것이 아니라 리뷰와 변경을 거치며 다듬어지는 것이라고 배웠기 때문입니다.

Q13. 너무 기본적인거라 묶어서 :

A13. 
    LEFT JOIN vs INNER JOIN
        한 줄 차이: INNER JOIN은 양쪽에 모두 일치하는 행만, LEFT JOIN은 왼쪽 테이블은 전부 유지하고 일치하는 오른쪽이 없으면 NULL로 채웁니다.

    트랜잭션이 하는 역할
        여러 작업을 하나의 단위로 묶어 전부 성공하거나 전부 취소되도록 보장하고, ACID 속성을 통해 장애나 동시 접근 상황에서도 데이터 정합성을 지켜줌

Q. 버튼 클릭시 참여 선착순 100명에게만 이벤트를 진행한다고 가정했을때

a. 동작원리를 아는대로 설명 : 
    사용자가 버튼을 클릭하면 서버에 API 요청을 보냅니다.
    서버는 로그인 여부, 중복 참여 여부를 확인합니다.
    현재 참여자 수가 100 미만일 때만 참여를 확정하고 기록합니다.
    결과(성공/마감)를 응답하고, 프론트는 화면을 갱신합니다.

    핵심은 판단(100명 넘었나)을 반드시 서버에서 한다는 점입니다. 프론트에서 막는 것은 UX일 뿐 보안이 아닙니다.

b. 고려 해야 할 상황은 무엇인가? :
    선착순 100명 이벤트에서 가장 먼저 고려해야 할 것은 동시성 문제(Race Condition) 입니다. 참여자가 99명인 시점에 여러 사용자가 동시에 요청하면, 서버가 각각 "99 < 100이니 통과"라고 판단해 101명 이상이 참여하게 될 수 있습니다. 그래서 "현재 인원을 조회하고, 100 미만이면 저장한다"는 두 단계를 따로 처리하지 않고, Redis의 INCR, DB의 조건부 UPDATE, 비관적 락처럼 하나의 원자적 연산으로 묶어야 합니다. 서버가 여러 대일 경우에는 synchronized나 서버 메모리 변수로 막을 수 없기 때문에, 모든 서버가 공유하는 Redis나 DB에서 처리해야 합니다.

    두 번째는 중복 참여입니다. 같은 사용자가 버튼을 연타하거나 여러 기기, 탭에서 요청을 보내면 한 사람이 여러 자리를 차지할 수 있습니다. 프론트에서 버튼을 비활성화해 UX를 개선하는 것과 별개로, 서버에서는 (event_id, user_id) 유니크 제약으로 DB 레벨에서 한 번 더 막고, 같은 요청이 반복되어도 결과가 같도록 멱등하게 처리해야 합니다.

    세 번째는 트래픽 폭주입니다. 이벤트 오픈 순간에 요청이 한꺼번에 몰리면 DB가 먼저 병목이 됩니다. 이를 줄이기 위해 카운트 처리는 빠른 Redis에서 하고, 마감된 뒤의 요청은 DB까지 가지 않고 즉시 "마감" 응답을 돌려주며(fail-fast), 필요하면 로드밸런서와 스케일 아웃, Rate Limit, 메시지 큐로 요청을 한 줄로 세워 처리합니다.

    네 번째는 프론트 우회와 어뷰징입니다. 버튼을 비활성화하거나 프론트에서 "마감" 표시를 하는 것은 편의일 뿐 보안이 아니므로, API를 직접 호출하면 우회할 수 있습니다. 따라서 인원 판단과 시간 검증은 항상 서버에서 하고, 매크로나 다중 계정 같은 악용은 로그인 인증, 계정/IP별 요청 제한, CAPTCHA 등으로 대응합니다. 이벤트 시작과 종료 시각도 클라이언트 시간이 아닌 서버 시간 기준으로 판단해야 합니다.

    다섯 번째는 장애와 데이터 정합성입니다. Redis에서는 카운트가 올라갔는데 DB 저장이 실패하거나, 서버가 중간에 죽는 경우 실제 참여자 수와 카운트가 어긋날 수 있습니다. 그래서 최종 기록은 DB에 남기고, 실패 시 재시도나 카운트 보정 로직을 두며, 이벤트 종료 후 Redis와 DB의 수치를 대조하는 점검 절차도 필요합니다.

    마지막으로 사용자 경험도 고려해야 합니다. 응답이 늦어질 때 로딩 상태를 보여 주고, 성공과 마감 결과를 명확하게 안내하며, 동시에 눌렀을 때의 우선순위 기준(서버가 먼저 처리한 순서)을 이벤트 정책으로 공지해 불필요한 분쟁을 줄여야 합니다.

가장 중요한 것은 동시성 문제로, 인원 확인과 저장을 원자적으로 처리해 101명 이상이 통과하지 않게 해야 합니다. 그 외에 중복 참여(유니크 제약), 트래픽 폭주(Redis, 큐, fail-fast), 프론트 우회와 어뷰징(서버 검증, 인증, 요청 제한), 장애 시 정합성(DB 최종 기록, 보정 로직)을 함께 고려합니다.

c. 100번째 버튼을 2명의 사용자가 동시에 눌렀을때 누구에게 우선순위를 부여할 것 인가 : 
    "동시"라는 것은 현실에서 없고, 결국 서버 어딘가의 단일 지점에서 요청이 직렬화되어 먼저 처리된 요청이 100번째가 됩니다. 클라이언트가 누른 시각이 아니라 서버가 먼저 처리한 순서를 기준으로 하며, 이를 원자적 연산으로 보장합니다.
    + INCR은 Redis가 단일 스레드로 처리해 두 요청이 같은 값을 받을 수 없습니다. 101, 102번째 요청은 즉시 마감 응답을 받습니다. 중복 방지는 SADD(Set)와 함께 쓰거나 Lua 스크립트로 한 번에 묶습니다.

    var, let, const : 한 줄 차이: var는 함수 스코프에 호이스팅 시 undefined로 초기화되는 옛 방식이고, let과 const는 블록 스코프에 TDZ가 있는 ES6 방식이며, const는 재할당이 불가능합니다.

Q. jwt는 프론트단 어디에 탑재되는가
A. 
    저장 위치는 크게 3곳(메모리 변수, Web Storage, 쿠키)이고, 요청 시에는 HTTP 헤더(Authorization: Bearer <token>)나 쿠키에 실려 전송, 질문이 "어디에 저장하나"와 "어디에 실어 보내나" 두 가지로 해석될 수 있어서, 둘을 구분해서 답하는 것이 안전

    1. 저장위치 : localStorage, sessionStorage, Cookie, Cookie (HttpOnly + Secure + SameSite), 메모리 (JS 변수, React state)

    2. 요청에 실어 보내는 방식 : 
        // 1) Authorization 헤더 (Storage/메모리에 저장한 경우)
        fetch("/api/me", {
        headers: { Authorization: `Bearer ${token}` },
        });

        // 2) 쿠키 (HttpOnly 쿠키는 브라우저가 자동 첨부)
        fetch("/api/me", { credentials: "include" });   // JS는 토큰을 볼 수 없음
